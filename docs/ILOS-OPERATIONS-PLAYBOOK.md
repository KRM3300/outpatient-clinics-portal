# ILOS — دليل إدارة وتطوير بوابة العيادات الخارجية / Product & Operations Playbook
الإصدار: مسودة اختبار 2026-11-06. المالك: إدارة العيادات الخارجية، مستشفى الرس العام.

## 1. حالة التشغيل / Release status
- دليل الموظف الذكي: تطبيق مستقل قائم، ويظل رابطه https://krm3300.github.io/opd-smart-guide/ دون تغيير.
- نسخة اختبار طلبات الطوارئ والمتابعة: https://krm3300.github.io/outpatient-clinics-portal/appointment-requests/test-live.html
- تجربة المريض: https://krm3300.github.io/outpatient-clinics-portal/patient-experience/ — واجهة تجريبية منفصلة، ولم تثبت جاهزية بياناتها الحية.
- اختبار المواعيد يستخدم Supabase؛ لا يوجد ربط مع VIDA ولا إشعار مريض فعلي. لا تدخل بيانات مرضى حقيقية قبل الاعتماد الأمني والمؤسسي.
- **تسجيل دخول موحد مع دليل الموظف الذكي لم يكتمل بعد**. لا تدّعِ اكتماله أو نشره.

## 2. صلاحيات المستخدمين / RBAC
| الدور | إنشاء طلب | قائمة الطلبات | معالجة الحجز | اعتماد الموظفين |
|---|---|---|---|---|
| pending | لا | لا | لا | لا |
| doctor / nurse | نعم في النسخة الحالية لكلا النوعين | طلباته فقط | لا | لا |
| scheduler | لا | جميع الطلبات | نعم | لا |
| supervisor | لا | جميع الطلبات | نعم | لا |
| admin | نعم | جميع الطلبات | نعم | نعم |

**تغيير مطلوب قبل الإنتاج:** فصل صلاحيات الطوارئ عن المتابعة وفق عضوية الخدمة، وتوحيد هوية الموظف عبر جميع الخدمات؛ الواجهة وحدها ليست حاجزًا أمنيًا. تحكم الخادم وسياسات RLS ضرورية. إدارة تجربة المريض تحتاج نموذج أدوار مستقل وتكاملًا آمنًا.

## 3. طريقة إضافة المستخدم / User onboarding
1. يفتح الموظف صفحة الاختبار، ويكتب البريد ويطلب رمز التحقق.
2. بعد الدخول لأول مرة، يكتب اسمه ويرسل طلب الصلاحية.
3. يبقى حسابه pending حتى يوافق مدير النظام.
4. يختار المدير الدور والحالة approved، ويختبر الصلاحيات من حساب تجريبي.
5. لا تجمع كلمات مرور الموظفين ولا تمنح صلاحية admin دون حاجة.
6. تعليق الحساب وتغييرات الصلاحيات يجب توثيقها في سجل مراجعة.

## 4. دورة العمل / Workflow
- طوارئ: طبيب/تمريض مخول → اختيار العيادة والطبيب والفترة → تأكيد إبلاغ المراجع بنظام الانتظار وأولوية أصحاب المواعيد → إرسال الطلب → موظف الحجز → قيد المعالجة/حجز مع مرجع/تعذر الحجز → توثيق الإشعار.
- متابعة: موظف مخول → اختيار العيادة والطبيب والفترة → رفع طلب متابعة → نفس قائمة موظف الحجز → المعالجة.
- لا يعد إرسال الطلب حجزًا مؤكدًا. التأكيد يتطلب إدخال مرجع من نظام الحجز المعتمد.
- القائمة الموحدة: تصفية حسب النوع والحالة، ومراجعة الطلبات المعلقة أولًا.

## 5. قاعدة البيانات / Database
- مزود الهوية والبيانات: Supabase Auth + PostgreSQL.
- الجداول الحالية: opd_appt_members، opd_appt_requests.
- التحكم: RLS وعمليات RPC مقيدة للصلاحيات، مع مراجعة جميع الدوال privileged قبل الإنتاج.
- لا تُعرض service_role keys في صفحات GitHub Pages.
- لا تستخدم بيانات مرضى حقيقية في اختبار GitHub Pages أو لقطات الشاشة.
- مطلوب قبل الإنتاج: مراجعة RLS، تحقق المدخلات، سجل تدقيق، سياسة الاحتفاظ والحذف، نسخ احتياطية، صلاحيات تجربة المريض، اختبارات أمنية، موافقة جهة العمل.

## 6. إدارة الواجهة والتطوير / UI & Development
- لغة عربية/إنجليزية، تصميم متجاوب، وضوح حالة الطلب.
- الهوية: استخدم **شعار مستشفى الرس العام المعتمد**، وليس رموزًا طبية متقاطعة. لا تستخدم أي علامة صليب في التصميم.
- لا تستبدل شعار المستشفى برسم تخميني؛ استخرج الأصل الرسمي المعتمد وراجع أذونات استخدامه.
- مصدر قائمة العيادات والأطباء: نسخة جدول Weekly OPD Schedule، وليست مزامنة لحظية. يلزم جدولة تحديث آمنة وفحص التكرارات والإجازات.
- الفروع: main للإصدار الحالي، feature/appointment-requests للتطوير؛ اختبر ثم راجع ثم انشر.
- التغيير: سجل طلب → تحليل أثر → تطوير → اختبار وظيفي وأمني → اعتماد → نشر → مراقبة → إغلاق.
- لا تعدل دليل الموظف الذكي أو جدولة تحديثه دون اختبار مستقل وحفظ نسخة احتياطية.

## 7. تعليمات حسب الدور / User instructions
### طبيب أو تمريض / Doctor or nurse
AR: سجل الدخول، اختر نوع الطلب المتاح، حدد العيادة والطبيب والتاريخ والفترة، تحقق من البيانات ثم أرسل. في الطوارئ أبلغ المراجع بوقت الحضور وأن المراجعة انتظار، والأولوية للمواعيد المسبقة.
EN: Sign in, choose your authorized request type, select clinic, doctor, date and session, review details and submit. For emergency requests, explain the arrival time, walk-in waiting process and priority for pre-booked patients.

### موظف الحجز / Scheduler
AR: افتح قائمة الطلبات، صفّها حسب النوع والحالة، تحقق من الطلب في نظام الحجز الرسمي، ثم أدخل المرجع وحدّث الحالة. وثّق الإشعار ولا تعتبر الطلب حجزًا قبل التأكيد.
EN: Open the unified queue, filter by type/status, verify in the official scheduling system, record the booking reference and update status. Document patient notification. Submission alone is not a confirmed appointment.

### مشرف / Supervisor
AR: راقب الطلبات المتأخرة والمتعثرة، راجع جودة البيانات وعمليات الحجز، وصعّد الانحرافات.
EN: Monitor delayed or failed requests, audit booking quality and escalate exceptions.

### مدير النظام / Administrator
AR: راجع طلبات انضمام الموظفين، تحقق من هوياتهم وصلاحياتهم الوظيفية، اعتمد الحد الأدنى من الصلاحيات، وراجع سجلات التغيير.
EN: Review staff access requests, verify identities and job responsibilities, grant least-privilege roles and review access changes.

## 8. معايير قبول الإصدار / Acceptance criteria
- حساب جديد لا يصل إلى البيانات قبل الاعتماد.
- كل دور يرى فقط الخدمات والطلبات المصرح بها من الخادم، وليس عبر إخفاء أزرار فقط.
- الطلبان يظهران لموظف الحجز في قائمة واحدة من أجهزة مختلفة.
- تصفية النوع والحالة تعمل، والحجز يحتاج مرجعًا موثقًا.
- لا توجد علامة صليب، والشعار الرسمي ظاهر بعد التحقق من الأصل.
- اختبارات عربية وإنجليزية وهاتف/حاسب، واختبار الرجوع والتراجع.
- لا تشغيل ببيانات حقيقية دون اعتماد الخصوصية والأمن.
